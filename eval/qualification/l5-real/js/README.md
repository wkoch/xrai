As três fontes de produção necessárias são a API pública em `react/src/ReactHooks.js`, a implementação/dispatch em `react-reconciler/src/ReactFiberHooks.new.js` e o agendamento em `react-reconciler/src/ReactFiberWorkLoop.new.js`. O requisito síncrono num root concorrente exige verificar essa segunda ligação. Os spans e hashes exatos estão em `oracles/source-relations.json`; isso é atribuição manual de fonte, com revisão semântica pendente, e não alegação de cobertura de call graph.

O pedido natural isolado está em `agent/input.md`. A futura materialização para braços deve fornecer **somente a árvore base completa e o pedido**, sem este diretório de dossiê, archive head, labels, patch ou probes. O materializador `run_l5_js.py` cria deliberadamente **workspaces do avaliador** com teste oculto; não é materializador de workspace do agente. A referência experimental aplica somente os dois módulos de produção do patch público, sem copiar a alteração de testes upstream. Oracle próprio: três requisitos comportamentais (incluindo notificação em `startTransition` fora de `act`, para não mascarar agendamento assíncrono) e duas regressões de state/effects. Esses testes não dependem de xrai, graft, Tree-sitter ou igualdade textual de patch.

Plano executável Linux descartável: Node16.20.2, Yarn1.22.22, instalação `--frozen-lockfile --ignore-scripts`, probes offline via `runner.execute(..., arbitrary_agent=True)` e verificação do teardown de namespace PID. O executor copia Node ao workspace e registra stdout/stderr completos limitados, exit, JSON Jest, hashes de executável/probe e lock antes/depois. Cada operação tem deadline de 300s. Recomenda-se pelo menos 2GiB livres por checkout/dependências; esse valor é preparo, não calibração de recurso.

A primeira tentativa Linux instalou o lock, mas Jest falhou antes de produzir relatório: `pretty-format` carregava o `react-is` bruto do workspace. O `postinstall` capturado contém `scripts/yarn/downloadReactIsForPrettyFormat.js` especificamente para corrigir essa colisão; `--ignore-scripts` omitiu esse passo. O executor agora reproduz apenas sua extração de dados, offline, usando [react-is17.0.2 oficial](https://registry.npmjs.org/react-is/17.0.2), que satisfaz `^17.0.1`. `setup/` preserva pacote, metadados de integridade SHA512/SHA1, SHA256 fixado, licença MIT e script upstream como prova. Antes dos probes, instala esses bytes sob `node_modules/pretty-format/node_modules/react-is`, valida lock e dependência e grava recibo `bootstrap.json`; nenhum hook é executado. O bootstrap mantém código de produção, lock e oracle intactos. Ambos os lados recebem o mesmo bootstrap.

Na [segunda execução Linux](https://github.com/wkoch/xrai/actions/runs/38280118706), bootstrap e teardown passaram: base falhou nos três requisitos por `Not yet implemented`, e as duas regressões passaram em ambos os lados. A referência falhou nos três requisitos com yields vazios. A análise das fontes capturadas identificou um erro do oracle anterior: `ConcurrentRoot` agenda `SyncLane` em uma microtask, enquanto nosso `act` síncrono drenava apenas Scheduler. Os testes upstream usam `await act` nas mesmas notificações. O pedido natural congelado exige atualização síncrona, sem exigir retorno na mesma pilha. O oracle agora observa o principal após **um único `await Promise.resolve()`**, mantendo `startTransition` fora de `act`, sem `flushSync` e sem drenar Scheduler. A regressão de state inclui o controle contrário: uma transição comum deve continuar pendente após o mesmo checkpoint. Lifecycle usa `await act`, como upstream. Oracle original, falha integral e anchors/hashes estão preservados em `docs/relatorios/logs/L5-continuacao/corpus-js/checkpoint-diagnostic/`. Essa é uma correção de observação; **não converte a segunda falha em sucesso**.

A [terceira execução Linux](https://github.com/wkoch/xrai/actions/runs/38282162955) preservou os três erros esperados da base. O controle de state chegou às suas assertivas, mas a regressão falhou porque React DEV avisou sobre a atualização de `Stateful` deliberadamente fora de `act`. O matcher upstream `.toErrorDev` agora exige somente esse aviso no callback da transição comum, restaura console e rejeita avisos adicionais. O principal permanece literalmente igual: sua store já notifica dentro de `batchedUpdates`, e a condição upstream para esse aviso exige `NoContext`. Nada é colocado dentro de `act` ou `flushSync` para ocultar o problema. Oracle anterior, falha e fonte do matcher/condição estão preservados em `corpus-js/third-warning/`; o guard rejeita aviso inespecífico e supressão global. **A terceira falha também permanece falha**.
