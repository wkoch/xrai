# Contrato mínimo M1 — revisão documental 2

**M0-01.R1 concretizado:** seletor fixo/`latest`, admissão e exemplos seguem
[L0-A02/A03](../relatorios/REVISAO-L0.md). A revisão documental 2 altera a forma
do request; `schema_version:2` e `fixture_version:2` identificam os pares atuais.
Os 25 pares v1 e seu schema permanecem, byte a byte, em
[legacy-v1](examples/legacy-v1/README.md). São históricos e o verificador atual
não os aceita por conversão implícita. Nenhuma API v1 foi publicada; esta
mudança não anuncia migração de banco ou compatibilidade de produto.

Entrega original **M0-01**, 11/10/2026; retificação **M0-01.R1**, 11/10/2026 (America/Sao_Paulo). Especificação normativa de domínio para M1;
**não anuncia APIs ou frontends implementados**. L0 só entrega o esqueleto
`xrai --help`/`--version`. A RFC continua autoridade arquitetural; as escolhas
locais abaixo concretizam seus ADRs 004, 005, 007, 009 e 012. Implementação dos
tipos é M1-01; o produto integrado depende dos gates G0/G1/G2.

**Escopo de plataformas do produto v1:** Linux x86_64 e macOS arm64, por
[decisão do usuário / ADR 020](../decisoes/PLATAFORMAS-V1.md). Isso não altera
`schema_version:2` nem a versão documental dos exemplos. Windows fica pós-v1;
representações já documentadas para ele são extensões futuras, não promessa
de execução ou portabilidade de bancos entre sistemas.

Fontes: [cartão M0-01](../PLANO-DE-IMPLEMENTACAO.md#m0-01--especificar-o-contrato-mínimo-e-o-escopo-da-alpha),
[RFC](../RFC-0001-ARQUITETURA.md), [validação](../PLANO-DE-VALIDACAO.md).
`examples/*.json` são pares completos de request/response e entradas adversas,
com bytes e hashes verificáveis. IDs e relógios das fixtures são ilustrativos;
nenhum resultado representa uma medição do xrai.

## 1. Identidade, paths e fonte

IDs públicos são strings opacas, independentes de rowid e número de linha.
Prefixos versionados nesta versão: `ws_`, `wt_`, `fi_`, `sym_`, `occ_`,
`snap_`, `cfg_`, `ctx_`, `item_`, `assert_`, `prod_`. Sufixo não vazio de
`[A-Za-z0-9_-]+`; consumidores não interpretam o sufixo. A geração é um
contador inteiro positivo local ao par workspace/worktree, sem significado
entre índices. Um ID completo sempre é resolvido junto à revisão/checkout.

| Identidade | Regra |
|---|---|
| Workspace | `workspace_id` identifica raiz/configuração de projeto; não depende de Git. O path de apresentação não é sua chave. |
| Worktree/checkout | `worktree_id` é próprio de cada checkout, inclusive sem Git; recriar raiz não herda automaticamente estado gravável. |
| Arquivo | `file_id` identifica entrada do inventário no checkout. A versão associa snapshot, path nativo, source hash e comprimento. Rename/move não implica linhagem automática. |
| Símbolo sintático | `symbol_id` associa versão de arquivo, frontend, kind, escopo lexical/owner e discriminador sintático. Homônimos, impls, receptores e funções anônimas não colidem. Em M1 é identidade sintática/lexical, sem estabilidade prometida após rename. |
| Ocorrência | `occurrence_id` associa símbolo/callsite, file version, hash e intervalo. Não confundir ocorrência com definição ou com alvo semântico. |
| Snapshot | `snapshot_id` identifica manifest imutável e geração publicada; referencia bytes, inventário, configuração e produtores. |
| Contexto | `context_id` identifica manifest imutável de seleção, retenção/expiração e snapshot(s); não é recibo ou memória do agente. |

Chave semântica futura: linguagem, pacote/versão, módulo, nome qualificado e
distinção de overload/escopo, quando comprovados. `semantic_key` e `lineage`
são `null` quando indisponíveis; não inferi-los de nome único ou similaridade.
Linhagem ambígua conserva candidatos ou cria ID novo. IDs antigos exigem seu
snapshot e nunca leem o arquivo atual silenciosamente.

Path de identidade é relativo à raiz capturada, nativo e sem perda:
`{"encoding":"unix_bytes","units_hex":"...","display":"..."}` usa pares
hexadecimais para bytes Unix; `windows_u16` usa grupos de quatro hexadecimais
para code units Windows, inclusive surrogate isolado. `display` é apresentação
e pode escapar bytes; nunca entra em comparação, resolução ou hash. Encoding
deve corresponder ao checkout. Não aplicar Unicode NFC/NFD, lowercase ou
conversão com substituição para criar identidade. Case, symlinks/reparse points
e caminhos longos são classificados pelo inventário: cada entrada mantém path
próprio; seguimento de links requer política explícita, limite de raiz e ciclos.
`..`, path absoluto e NUL não entram no path relativo de uma fonte.

No produto v1, o aceite nativo cobre `unix_bytes` em Linux/macOS. A forma
`windows_u16` e suas fixtures permanecem para evolução do contrato; não exigem
adapter Windows, testes de reparse points ou execução Windows em M1. Não
coagir encodings incompatíveis para abrir um checkout no host atual. Preservar
CRLF e bytes originais continua obrigatório independentemente do SO.

Fonte é o buffer original; preservar CRLF, BOM e bytes multibyte. Hash canônico
é `{"algorithm":"blake3","hex":"<64 hex minúsculos>"}`, digest de 256 bits
sobre **todos os bytes do blob**, não sobre texto normalizado ou só snippet.
`byte_length` é o tamanho do blob. `span={"start":n,"end":m}` é `[n,m)`,
com inteiros `0 <= n <= m <= byte_length`. Fonte textual M1 requer UTF-8 válido
e limites de span em boundaries UTF-8. Arquivo não UTF-8 é preservado no
inventário/blobs com diagnóstico e não convertido com perda. Path não UTF-8
continua válido. Arquivo vazio possui hash do buffer vazio, parse válido e
zero símbolos; não é erro nem capacidade ausente.

`content` de item de fonte deve ser exatamente `blob[start:end]` decodificado
UTF-8. Trechos descontínuos são itens separados, com seus spans; não simulam
fonte contínua. Linhas de apresentação são base 1; colunas UTF-8 em bytes são
base 0, com unidade declarada. Conversão UTF-16 externa é explícita e não
altera identidade. Hash/span inválido rejeita publicação/retorno.

## 2. Revisão, derivação e afirmações

Snapshot contém `snapshot_id`, `workspace_id`, `worktree_id`, `generation`,
`input_kind` (`captured_blobs`, `git_commit` ou `worktree_capture`),
`configuration_id`, `configuration_fingerprint`, `producer_fingerprint` e
`captured_at` UTC RFC3339. `git_commit` exige object ID/algoritmo no manifest;
`worktree_capture` não afirma atomicidade global. Uma revisão experimental
base/head mantém **dois snapshots identificados**; cada item/aresta indica seu
snapshot. Sem base/head explícito só um snapshot é permitido por resposta.

Produtor registra `producer_id`, `name`, `version`, `fingerprint` (BLAKE3),
`frontend`, `grammar_version` e `method` (`syntactic`, `semantic_resolution`,
`framework_rule`, `observed_runtime`, `inferred`). Versão/gramática ainda não
escolhidas não podem gerar fato de produto. Fixture usa produtor `fixture`,
sem executar parser. Configuração tem ID/fingerprint, condições conhecidas
(target, features, build tags, ambiente), com estados `known`/`not_evaluated`.
Afirmações herdam produtor/configuração **da mesma revisão** e referenciam
evidências: file ID, snapshot ID, source hash e span.

Derivação lista entradas positivas e negativas: blobs, manifests, regras,
configuração e dependências cuja ausência foi observada no escopo. Novo
export, mudança de config, path ou gramática invalida resoluções pertinentes;
sem granularidade suficiente, invalidar conservadoramente. Reuso sintático
por hash/produtor não autoriza reuso semântico sem path/pacote/dependências.

Afirmação é união discriminada pelo campo `state`:

| State | Conteúdo permitido e significado |
|---|---|
| `resolved` | Exatamente um `target_id`, evidências, método e condições. Em M1 estrutural: `contains`/`defines`; calls resolvidas só no recorte promovido. |
| `candidate` | `candidate_ids` não vazio, `reason`, evidências. **Sem** `target_id`; ranking não muda o state. |
| `external` | Identidade externa verificável e `reason`; não criar símbolo local fictício. |
| `unknown` | `reason`, evidência do callsite/limite quando reconhecido; **sem** target/candidates confirmados. |

`calls`, `references`, imports sintáticos e contenção são relações distintas.
Sintaxe de chamada comprova callsite, não alvo. Fatos resolvidos (locais ou
`external` identificados), candidatos e
unknowns ocupam arrays separados (`assertions`, `candidates`, `unknowns`);
candidato não desserializa como fato. Probabilidades não são emitidas sem
calibração; score de busca é relevância. Nenhum import, macro, `build.rs`, cgo,
script ou build do projeto é executado durante indexação.

## 3. Três dimensões independentes

`index.availability`: `ready`, `not_indexed`, `rebuilding` ou `failed`.
`rebuilding` pode servir snapshot anterior explicitamente fixado. Banco ausente
não equivale a parse válido vazio. Uma geração parcial pode estar disponível.

`support`: `supported`, `experimental` ou `unsupported`, acompanhado de
`capability`, linguagens/escopo, produtores, limites e motivo. Registro de
capability informa `available` e estágio atual; item indisponível nunca vira
ferramenta anunciada como executável. Uma operação pode ser suportada com
parte dos arquivos fora do frontend; isso se reflete também em coverage.

`coverage` não é probabilidade de acerto:

* `inventory`: escopo/denominador explícitos, contagens de elegíveis,
  processados, parciais, falhas, desatualizados, capacidade ausente e excluídos.
  Elegíveis são a soma das cinco categorias de processamento; excluídos ficam
  fora desse denominador mas dentro do universo descoberto. `files` conserva
  motivos/ranges mesmo sem nenhum símbolo.
* Cada arquivo: `processed`, `partial`, `excluded`, `failed`, `stale` ou
  `capability_absent`. `processed` + `tree_valid=true` + `symbol_count=0`
  distingue extração vazia válida. `partial` registra gaps `[start,end)`;
  falha pode ter intervalo desconhecido (`null`). Exclusão tem regra/motivo;
  parser ausente é `capability_absent`, não sucesso.
  `symbol_count:null` indica que não houve extração/contagem observada (por
  exemplo, exclusão ou parser ausente); não inventar zero nessas situações.
  Somente parse válido processado com `tree_valid:true` e `symbol_count:0`
  comprova extração vazia válida.
* `relations`: reconhecidas/resolvidas/externas identificadas/candidatas/unknown, domínio e
  denominador `recognized_occurrences` ou `not_available`. Extrator pode
  deixar ocorrências não reconhecidas: razão resolvidas/reconhecidas não mede
  recall real. Sem resolver, contagens são `null`, não zeros completos.
* `query`: `complete`, `partial` ou `unavailable`, no universo/recorte
  explicitado; gaps pertinentes sobrevivem em resultados positivos e vazios.
  `complete` é exaustivo **somente nesse recorte e revisão**, conforme limites
  declarados, sem precisão semântica universal. `no_recorded_issue` não prova
  completude de extração nem precisão. Exclusão declarada pode permitir
  completude no escopo elegível; se arquivo excluído for âncora pedida, a
  resposta é parcial/indisponível, nunca desaparece silenciosamente.

`sufficiency`: `satisfied`, `not_assessed`, `incomplete` ou
`insufficient_budget`; obrigações `identified`, `included` e lista de omissões
com `required`, `reason` e continuação. `satisfied` quer dizer que obrigações
identificadas cabem e foram entregues, sem assegurar sucesso de qualquer tarefa.
Operações sem planner podem satisfazer o resultado solicitado dentro do
recorte, sem alegar suficiência para implementar correção.

`status`: `ok`, `partial`, `insufficient_budget` ou `error`. Precedência:
request inválido/erro operacional ou capability unsupported → `error`;
obrigação obrigatória omitida por orçamento → `insufficient_budget`;
outra lacuna pertinente → `partial`; restante → `ok`. `insufficient_budget`
preserva também lacunas semânticas/frescor; `partial` **nunca** encobre falta
de tokens/bytes. Paginação/truncamento de resultado marca `partial` e cursor;
obrigação não entregue por limite de resposta usa `insufficient_budget`.

Resultado vazio completo requer índice disponível, operação suportada,
universo pesquisado definido, snapshot coerente, query completa e nenhuma
omissão obrigatória. Só comprova ausência de correspondência na consulta,
nunca ausência de chamadas no programa sem resolver apropriado.

## 4. Consistência e retenção

A entrada usa `consistency.revision` como união discriminada:
`{"kind":"fixed","snapshot_id":"snap_..."}` ou `{"kind":"latest"}`.
`latest` é seletor; nunca um `snapshot_id`. A resposta sempre declara o ID
da geração efetivamente usada. `status` com `latest`, antes da primeira
publicação, pode retornar `snapshot:null` e `index.availability:not_indexed`.

| Seleção/modo | Garantia e falha |
|---|---|
| `fixed` + `snapshot` | Lê somente o ID pedido. Snapshot não retido resulta `snapshot_expired`, sem rebind. Não afirma frescor do filesystem. |
| `fixed` + `validated/strict` | Valida o escopo exigido para o ID pedido. Se mudanças conhecidas exigem outra geração, retorna `snapshot_stale`, mesmo que o ID original ainda esteja retido; nenhuma fonte/fato e orientação para consulta nova explícita. Não chamar stale de expiração. |
| `latest` + `snapshot` | Fixa a geração publicada disponível no início da consulta. Informa seu ID, sem reconciliar ou afirmar filesystem atual. |
| `latest` + `validated` | Reconcilia bytes, configuração e dependências pertinentes antes de fixar a geração da resposta; geração nova é permitida e explícita. Busca global reconcilia universo incluindo arquivos novos/removidos, nunca somente hits anteriores. |
| `latest` + `strict` | Reconcilia todo o escopo solicitado, inventário e dependências necessárias antes de fixar a geração. Se validação não conclui, registra gaps, `validation_incomplete`/`unstable_input`, query incompleta e `partial` (ou `insufficient_budget` por fonte obrigatória que não cabe). |

Sem validação concluída, `fixed` e `latest` em validated/strict conservam
diagnóstico e ausência de completude. Não mudar geração de `fixed` para
concluir a validação. Âncora (`symbol_id`, `occurrence_id`, âncora contextual)
incompatível com a geração resolvida exige `anchor_revision_mismatch` e
nova consulta/relocação explícita. Coincidência de nome não migra identidade.

`freshness` informa mode, `validated_scope`, `validated_at` (`null` em snapshot),
`validation_complete`, `atomicity` (`captured_blobs`, `immutable_commit` ou
`non_atomic_worktree`) e gaps. `strict` no working tree continua sem snapshot
atômico universal: alterações durante captura exigem retry limitado e lacuna
de instabilidade. Watcher, mtime e tamanho não substituem hash. Fonte/fatos
sempre pertencem ao snapshot declarado; alteração detectada permite nova geração
para `latest`, ou rejeição tipada para `fixed`. Overlays não salvos e hidratação
cross-worktree são futuros, não capacidades L0/M1 básicas.

Snapshots/contextos/cursors possuem retenção configurada e expiração; produtor
anuncia duração/política quando implementado, sem TTL fictício no contrato.
`expand` fixa snapshot(s), manifesto e seleção anterior, com novos limites;
IDs expirados geram erro tipado e instrução de repetir consulta. Cursor opaco
fica preso à geração, operação, consulta, ordem estável e escopo. Nada muda de
revisão para completar página/expansão.

## 5. Request/response e limites

JSON UTF-8 compacto, schema version documental `2`. Request contém `request_id`,
`workspace_id`, `worktree_id`, `operation`, `consistency`, `limits`, `params`.
`consistency` exige mode, seletor `revision` e scope declarativo: `workspace`
para todo o checkout; `path_prefix` com path nativo relativo; ou `files` com
IDs explícitos. Validated/strict reconciliam todo o inventário do recorte,
inclusive novos arquivos/removidos. Scope de files vazio só é válido para
status do checkout. `status` + `latest` antes da primeira geração pode ser
`ok`, `snapshot:null`, `index.availability:not_indexed`,
`sufficiency:not_assessed` e `coverage.query:unavailable`, sem fonte/grafo nem
completude. Freshness usa `atomicity:none`, validação incompleta e instante
`null`; não inventa revisão. `expand` e requests com cursor exigem seletor
`fixed` igual à revisão do manifesto original, inclusive quando existe outra
geração publicada. Expiração conserva erro próprio e nunca muda o manifesto.
`params` é discriminado por operação; campos desconhecidos são recusados.

| Operação | Params e capacidade exigida em M1 |
|---|---|
| `status` | `{}`; inventário/capabilities/revisão, incluindo indisponibilidades |
| `search` | `query` não vazia, `channel` = `name`/`path`/`text`, `cursor` opcional; `search.lexical` |
| `inspect` | `file_id` ou `symbol_id`, exatamente um; `view` = `source`/`signature`/`outline`, `cursor` opcional; `inspect.source`/`inspect.outline` |
| `relations` | `symbol_id`, `kind` = `contains`/`defines`/`references`/`calls`/`impact`, `direction` = `in`/`out`, `cursor` opcional; capability por kind |
| `context` | `intent` = `locate`/`understand`/`fix`/`review`/`impact`, `description`, `anchors` e diff/base/head opcionais; `context.experimental` no recorte aprovado |
| `expand` | `context_id`, `item_ids` não vazios; `expand.experimental`, mesma geração |

`index`, `map`, `mcp` são comandos/adapters M1 planejados, não novas
ferramentas MCP. Acesso a impacto em M1 usa `relations(kind=impact)` ou
`context(intent=impact)` no recorte promovido; sem resolver retorna erro de
capability. Comandos separados `impact` e `export` na RFC são propostas sem
tarefa/aceite M1, portanto não anunciados pela alpha. MCP inicial tem somente as seis
operações implementadas efetivamente; anúncio negocia disponibilidade real.
Fallback não é implícito: `next` orienta `search` textual/inspect e rotula seus
resultados como candidatos, respeitando exclusões e escopo.

`limits` exige `max_bytes` positivo; aceita `max_tokens`/`tokenizer` juntos ou
ambos `null`, `deadline_ms`, `max_candidates`, `max_files`, `max_source_bytes`
e `max_expansions`, todos positivos (expansions pode ser zero). São limites
duros de trabalho e saída, não despesas financeiras. O produtor publica caps
configurados, recusa ultrapassagens ou reduz trabalho com diagnóstico explícito.
CPU/I/O/candidatos/expansões esgotados geram `partial` + gap específico; fonte
necessária que não cabe em saída gera `insufficient_budget`.

Envelope normal tem `schema_version`, IDs do request/checkout, `status`,
`snapshot` (ou `null` em erros sem snapshot/status antes de geração), `index`, `support`, `freshness`,
`coverage`, `sufficiency`, `budget`, `items`, `assertions`, `candidates`,
`unknowns`, `omissions`, `diagnostics`, `next`, `error` (`null` sem erro).
Itens incluem ID, tipo/view, file/snapshot/hash/span quando têm fonte, motivo
e produtor/configuração; `context_id` e `cursor` existem quando pertinente.
Erros sem snapshot não carregam fonte/grafo nem afirmam cobertura completa.

Contagem de `budget.used_bytes` cobre **todo o envelope normal serializado**
incluindo metadados, escapes, omissões e o próprio campo de contagem; resolve-se
até valor estável. Wire é JSON compacto sem BOM/newline; `ensure_ascii=false`
nas fixtures. stdout CLI JSON não adiciona framing; wrappers MCP controlados
pelo xrai também entram na conta no adapter, que recalcula antes de enviar.
As fixtures contam somente envelope do domínio e declaram esse alcance em
`budget.counting_scope`. Wrappers do cliente/conversa externa não são controlados.

Tokens exatos só com perfil/tokenizer/version fixado e confirmado em M0-09;
L0 **não escolhe nem anuncia tokenizer exato**. Para perfil ausente: tokens
`null`; para estimativa: perfil, método e margem explícitos, sem promessa de
teto token exato. M1-16 deverá comprovar ao menos um perfil exato. `max_bytes`
continua duro em ambos os casos. `budget` reporta requested/used bytes e
requested/used tokens, counting (`exact`/`estimated`/`not_requested`) e tokenizer.
Tetos por tentativa/sucesso dos gates e orçamento financeiro de campanha são
registrados no harness; não reutilizar max_tokens de uma resposta como custo
da sessão. Recibos e saldo agregado entre chamadas são posteriores.

Antes de recuperar fonte, calcular envelope mínimo admissível no perfil
solicitado. Se não cabe, recusar admissão com `request_budget_too_small`,
sem JSON truncado ou resposta normal acima do teto. CLI: stdout vazio, exit 2,
diagnóstico em stderr. MCP: erro de execução da ferramenta (`isError:true`),
com JSON-RPC preservado; argumentos malformados continuam erro de protocolo.
A versão MCP deverá ser fixada no spike do adapter, sem alegar adapter pronto.

O cap **4096 bytes** limita a serialização controlada pela aplicação: bytes
UTF-8 de stderr na CLI; objeto MCP `result` completo incluindo `content`,
`structuredContent` se usado, escapes e `_meta`. Representação duplicada é
contada duas vezes. Framing JSON-RPC e ID ecoado são medidos no custo total,
mas ficam fora desse cap da aplicação. IDs arbitrariamente longos não recebem
promessa de wire universal <=4096; limites de entrada/transporte pertencem ao
adapter. As fixtures medem o objeto JSON-RPC compacto, sem framing de
transporte, e declaram essa unidade.

Mensagens/campos do diagnóstico são limitados; não reproduzir paths,
descrições ou IDs extensos, nem fonte. Se detalhe excede cap, usar diagnóstico
mínimo válido. Registrar `minimum_counting:exact` somente com mínimo
comprovado; estimativa usa `estimated_admission_bound` e método explícito.
Os valores de admissão dos exemplos são limites **ilustrativos estimados**,
não contagens de mínimo de um adapter ou tokenizer implementado.

`retry_automatically:false`: não repetir orçamento impossível nem aumentá-lo
silenciosamente. Consumidor decide nova solicitação; diagnóstico e eventual
repetição entram no custo da sessão/experimento. A exceção comunica rejeição,
sem fingir cumprir `max_bytes` pedido. Fixtures 14/25/26 mostram serializações
documentais; medição real de CLI/MCP e tokens pertence a M0-09/M1-16/17/18.

## 6. Erros, saída e cancelamento

| Código | Condição | Exit CLI M1 |
|---|---|---|
| nenhum | `ok` | 0 |
| nenhum | `partial` ou `insufficient_budget` | 3 |
| `invalid_request`, `invalid_span`, `request_budget_too_small` | argumentos inválidos/inadmissíveis | 2 |
| `unsupported_capability`, `index_unavailable`, `snapshot_expired`, `snapshot_stale`, `anchor_revision_mismatch`, `context_expired`, `cursor_expired` | indisponibilidade explícita; next orienta recuperação | 4 |
| `source_mismatch`, `producer_mismatch`, `storage_error`, `resource_limit` | erro operacional/integridade | 5 |
| `cancelled` | cancelamento pedido, sem corrupção/publicação incompleta | 130 |

Diagnóstico possui `code`, `message`, scope/file/span opcionais e `retryable`.
`error` não nulo só em status error; request inválido pode ser recusado antes
do envelope. Prazo/cancelamento não publica fatos incompletos como geração
válida. Cancelar cliente não cancela trabalho compartilhado necessário a outro.
CLI stdout só dados; stderr logs/progresso. MCP preserva IDs, isola clientes,
negocia versão e projeta o mesmo motor. Batch futuro só com limite agregado
explícito, não multiplicação de envelopes ilimitados. TTY é projeção humana,
sem mudar significado ou revisão.

## 7. Matriz sintática M1 prometida (ainda indisponível em L0)

Todos os frontends usam extração comum M1-06: declarações, scopes, contenção,
assinaturas, imports e callsites **sintáticos**, posições/diagnósticos e
fingerprint. Fonte incompleta preserva fatos válidos fora de gaps e fica parcial.
Contagem de símbolos não é avaliação de precisão.

| Frontend/dialetos | Formas prometidas | Limites explícitos e aceite responsável |
|---|---|---|
| Rust `.rs` | módulos inline/externos declarados; funções (incluindo async/genéricas); structs/enums e membros; traits, impls e métodos; aliases, const/static; use simples/agrupado/alias/glob; scopes de outline, atributos e condições observáveis | M1-07: spans/contenção e impls homônimos distintos; `cfg` não avaliado e macros não expandidas são limites; nenhum `flush`/`take` resolve por nome; não executar build.rs |
| JS `.js`, `.mjs`, `.cjs`; JSX `.jsx` | funções declaradas/expressões/arrow atribuídas; classes, métodos, scopes e funções anônimas; imports/exports ES e reexports distintos; CommonJS literal `require("...")`, `module.exports = ...`, `exports.name = ...` como sintaxe | M1-08: dialeto determinado por extensão/config explícita, nunca fallback de gramática silencioso; JSX conserva spans; require calculado/dynamic import/callback/decorator não confirma alvo |
| TS `.ts`, `.mts`, `.cts`; TSX `.tsx` | formas JS acima, interfaces/types, assinaturas e membros TS; generics, classes e funções atribuídas; imports/exports/reexports | M1-08: namespaces/augmentation e overloads sem prova não ganham semântica; tsconfig alias é configuração, resolução só no recorte promovido; TSX não desloca bytes |
| Python `.py`, `.pyi` | classes; funções sync/async; métodos e funções aninhadas; imports absolutos/relativos sintáticos; associação de decorators/docstrings; escopos, assinaturas e declaração de stub | M1-09: indentação/multiline/Unicode corretos e homônimos distintos; imports não executados; getattr, monkey patching, módulos calculados, efeitos de decorators não resolvidos |
| Go `.go`, inclusive `_test.go` | package/import; funções e métodos/receptores; structs/interfaces, campos/embedding; tipos/aliases, genéricos, const/var relevantes; build constraints observáveis | M1-10: receptores distintos, interface/embedding só declaração; tags não avaliadas explicitadas; make não resolve cross-language; cgo/go generate não executados; convenção de nome de teste não prova coverage |

Versões de gramáticas/dialetos serão fixadas e provadas por M0-05/M1-06 e
registradas nas capabilities. A matriz define formas, sem anunciar suporte a
qualquer versão futura de linguagem. Forma fora da matriz retorna limitação,
não relação resolvida. Cada frontend deve entregar fixtures rotuladas para
todas as formas contratadas, incompletude, Unicode e homônimos no cartão.

M0-02 provou o scaffold na matriz histórica de três SOs observada em L0;
M0-02.R2 adequa a CI ao v1. Isso ainda não comprova gramáticas/parsing de
M0-05 nem a distribuição da alpha em Linux x86_64 e macOS arm64. M1-01 só após G0; engenharia ampla M1-02+
só após G1. `status` deve refletir estado real, nunca inferir disponibilidade
porque existe este contrato. P2/P3 ficam experimentais e delimitados, sem
promessa de semântica geral, suficiência universal ou economia para toda tarefa.

Fora da disponibilidade M1: resolvers amplos/impacto sem prova (M2/M3),
embeddings, slicing semântico, propósito curado, memória de investigação,
recibos/deltas, hidratação entre worktrees, ingestão de SCIP/LSP pelo produto,
ligações gerais cross-language e seleção que autoriza omitir testes. Oracles
externos do avaliador não anunciam essas capacidades no produto. Testes podem
ser priorizados como candidatos; ausência de resultado não dispensa suíte.

## 9. Exemplos e verificação M0-01

Fixtures trazem `fixture_version:2`, `fixture_files` (paths, bytes hex,
snapshot IDs), request, response, expectativa e `fixture_state`. Este último
é oracle documental externo à API: geração publicada, geração requerida pela
reconciliação, snapshots retidos, vínculos de âncoras/manifests e inventário/hash
esperado após reconciliação. O verificador compara resposta a esse estado
controlado; ele não consulta filesystem real nem executa reconciliação. `valid=false` significa entrada que o contrato
deve **rejeitar**, não erro legítimo do produto (erro legítimo é valid=true).
Contadores/símbolos das fixtures são rotulados manualmente a partir dos bytes;
nenhum parser foi executado para produzi-los. Hashes e tamanhos são calculados.
[schema.json](examples/schema.json) é schema JSON Schema 2020-12 para pares;
[verify.py](verify.py) verifica semântica adicional: source/hash/spans UTF-8,
contadores, revisão, unions, orçamento e erros. Não implementa API de M1.
Schema/verificador cobrem as formas usadas nestes exemplos; não são validação
completa do domínio ou das representações futuras. As invariantes normativas
dos dois alvos do v1 exigem implementação/testes em M1-01; paths Windows
adversos e runtime Windows ficam para a expansão posterior.

|---|---|

Execução reproduzível de desenvolvimento (bibliotecas não entram no binário
nem são requisito de uso): `python3 -m pip install --target /tmp/xrai-contract-check -r docs/contracts/examples/requirements.txt`,
depois `PYTHONPATH=/tmp/xrai-contract-check python3 docs/contracts/verify.py`
e `PYTHONPATH=/tmp/xrai-contract-check python3 -m unittest discover -s docs/contracts/tests -v`.
Os dez testes incluem rejeição adversa, `main` não zero quando caso inválido é
rotulado `valid:true`, falsa aceitação/rejeição inesperada injetadas e um
processo real com fixture adulterada. `--examples <diretório>` permite executar
esse testemunho sem mudar fixtures versionadas. Exceção inesperada não é
convertida em sucesso.
São hashes reais calculados sobre bytes da fixture; tamanho serializado também
é medido, não placeholder. Validação destes exemplos não prova parser,
filesystem, banco, tokenizer, semântica ou APIs futuras. Esses aceites têm os
cartões responsáveis acima.
